## 1. 目的

複数の機能で共有する処理を`app`内の`core`パッケージへ集約し、機能固有の実装が他の機能へ広がることを防ぐ。

## 2. 構成

| 領域 | 責務 |
| --- | --- |
| `core/common` | 共通の型、結果、エラー、ユーティリティ |
| `core/ui` | テーマ、共通コンポーネント、表示ルール |
| `core/storage` | SQLiteを含むローカル保存の共通基盤 |
| `core/firebase` | Firebaseを利用する場合の初期化・認証・通信境界 |
| `core/notifications` | 通知登録や通知表示の共通処理 |

実際に複数機能で必要になった領域だけをパッケージとして追加する。空の抽象化や将来用途だけの共通層は作成しない。

### 共通アプリシェル

`core/ui`の`TinyworksAppShell`が、全機能に共通する画面外枠を提供する。

- ステータスバーを避けた紫色の上部ヘッダー
- `Tinyworks`のアプリ名表示
- 右上のハンバーガーメニューからホームと各機能へ遷移する右側ドロワー
- ドロワーはスワイプでは開かず、ハンバーガーボタンのタップで開く
- 端末のナビゲーションバーに重ならない下部余白
- 機能名や遷移先は`app`がメニュー項目として組み立てる

`core/ui`は`home`や各機能へ依存せず、メニュー項目のラベル、選択状態、遷移処理を受け取って表示する。機能画面は共通アプリシェルのコンテンツ領域へ配置する。

## 3. 依存関係

- `core`から`feature`へ依存しない
- 機能固有の業務ルールを`core`へ置かない
- `feature`間の直接参照を避ける
- `app`が機能間の組み立てと全体ナビゲーションを担当する

初期段階では一つのGradleアプリモジュール内でパッケージ境界を守る。規模が大きくなった場合だけ、境界を保ったままGradleモジュールへ切り出す。

## 4. 保存方針

- 個人用データは端末内保存を基本とする
- 保存方式は機能の要件に応じて選択する
- 機能固有のデータモデルやRepositoryは各`feature`側で管理する
- `core/storage`はSQLiteデータベースの生成、接続、モジュール登録、共通のマイグレーション境界を提供する
- 各機能は専用のテーブル、スキーマ、Repositoryを`feature/<機能名>`側へ閉じ込める
- `core/storage`は特定機能のテーブル名や業務ルールを直接参照しない
- 機能追加時はSQLiteモジュールを登録し、既存機能のテーブルへ直接依存しない

### SQLite構成

```text
core/storage
└─ TinyworksDatabase
   ├─ 共通SQLiteOpenHelper
   ├─ 機能ごとのDatabaseModule登録
   └─ DBバージョン更新・マイグレーション呼び出し

feature/pomodoro
├─ PomodoroDatabaseModule
├─ pomodoro_settings
├─ pomodoro_sessions
└─ PomodoroRepository
```

SQLiteは端末内にのみ保存する。クラウド同期、Firebaseデータサービス、アカウント情報は共通SQLite基盤へ追加しない。

## 5. Firebase方針

- Firebase App Distributionはアプリ配布用途として利用する
- Firebase SDKは、アプリ内の要件が確定した機能だけ導入する
- Firebaseの認証・データアクセスを追加する場合は、権限、ルール、プライバシー方針を同時に定義する
- Firebaseを利用しない機能へ、共通処理としてFirebase依存を持ち込まない
